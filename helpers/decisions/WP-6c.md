# WP-6c — decisions and assumptions (integration dry run + skills red-team)

Brief: `helpers/decisions/TG-PHASE-6.md` §1 and §1.3. Outcomes per finding and attack: `helpers/status/WP-6c.md`.

## Process
1. **No live call of any kind.** The core and pack run inside `vendor/helpers/tests/harness/gas-mocks.js` (vm context, mock Drive/Sheets/Telegram/UrlFetch); the skills run on scratch copies of the pack's invented fixtures (`transit-city`, `port-sorrel`) under `--out`; Maps and web fetch are the drivers' offline/fixture modes. The wake route is the harness's `getEvent` call, never an HTTP request.
2. **Nothing under `vendor/helpers/` was edited.** Every pack, core or tools change is a REQUEST with a patch in the status file. The private repo gains one tool, skill fixes and docs.
3. **Re-stamping `created_at`.** `envelope.mjs` stamps envelopes with wall-clock time (2026-10), while the dry run's mock clock sits in 2027 so the fixture trips are "upcoming"; the core refuses an envelope created more than 14 days before its clock. The tool therefore validates each payload with `envelope.mjs` (the real stamp path), then rewrites `created_at` and the file-name stamp to the mock clock before dropping the file into the mock `from-brain/`. The validation result is what the skills would get in production; only the timestamp is adjusted. A `--now` option on `envelope.mjs` would remove the need (REQUEST R1, optional part).
4. **One deliberate refusal.** The chat step answers a fresh request once with `html: "yes"` to prove the core refuses it (`envelope_rejected`, request stays open) and then with a boolean reply. The ledger check allows exactly that one audit row; any other refusal fails the run.
5. **Red-team runs on a copy.** Hostile research/plan inputs run against `OUT/redteam-repo`, a copy of the journey scratch repo, so the journey memory can be checked afterwards for leakage (no fixture marker, no tags) independently of the hostile runs.

## Skill-side defaults chosen
6. **Clean, don't refuse, free text from requests.** `destination`, country, `lodging`, `booked`, candidate names and the replan `reason` are stored as data after `cleanText`: tags `<[^>]*>` removed, control characters removed, whitespace collapsed, clipped to the schema (destination 120, lodging 500, booked 300, reason 300, names 120). Refusing would drop a whole round for one stray character. Dates stay strict (refused when invalid). The pack already caps its own owner inputs, so clipping only bites on a hand-edited request — **architect decision 2: keep the clip; recorded as the default.**
7. **Seeds** are kept only when plain: a URL (`://` or `www.`), markup (`<` `>`), a slash command (`^/`) or more than 80 characters is dropped and listed in `brief.seeds_dropped` (≤ 20 seeds kept). A dropped seed is reported in the reply, never searched.
8. **`lodging` / `booked` from the `research` request** become `Staying:` / `Booked:` lines under `## Owner notes` in `trips/<slug>.md` (one `Staying:` line per trip; a new one replaces it). The `Staying:` line is never parsed into the data block; the *located* lodging comes from the lodging step (16 below — **architect decision 1, option (a)**). The dry runs run that real step; the earlier `routineLodgingStep` stand-in is gone.
9. **Replan deliverables.** The pack's `replan` request carries no `deliverables`. The skill defaults to `['plan', 'brochure']` when the trip's latest build has a brochure (Trips tab `drive_brochure_html/pdf` in the dry run; `builds[]` in `trips/<slug>.md` in production), else `['plan']`, and re-attaches the html/pdf ids on the reply. When REQUEST R3 lands the request's field wins.
10. **Review closes the trip.** `prefs-build-review.mjs` sets `trips/<slug>.md` status `done` once at least one place was rated, skipped or already recorded and the status is not `done` yet (the pack sends the `review` request on ✅ Finish). Before, trips stayed `delivered` forever. **Architect decision 3: accepted as is; flagged for Phase 8** — if the pack ever sends a `review` request before ✅ Finish (a partial review), `done` should move to the Finish-only path.
11. **`places` check always answered.** `trip-check-run.mjs --digest always` writes the digest even when nothing changed; the weekly routine keeps the silent behaviour (no flag). A request must always get an envelope or the core keeps it open for 24 hours.
12. **`chat-check.mjs`** refuses a non-boolean `html` (mirrors the core). Plain-text replies rely on the core's escaping; `html: true` is used only for text the skill composed itself, never for untrusted content.
13. **Q-1 publisher wiring** is backward compatible with the Phase 5 vendored research kit: the skill passes `{ distinct: 'publisher' }` (ignored by the old kit) and dedupes per place by `publisher || ref` itself; `publisher` is lower-cased, ≤ 120, and only added to the mention when present. When the Phase 6 kit lands, the kit's own `distinct` makes the skill-side dedupe a no-op.
14. **Interview text answers** in the dry run are invented (`the lantern museum, a bakery on Harbour Lane`); they exist only to force the "always held → review → decisions" path, since pick/scale answers are confirmed directly and never produce a `decisions` request.
15. **Dry-run button selection** uses the newest keyboard only (`lastKeyboard`), so a stale earlier keyboard with the same label can never be tapped by accident — the same as a real owner tapping the message in front of them.

## Lodging step (architect decision 1, option (a))
16. **When it runs.** In the `new` round, after `trip-research-start`, only when the request carries `lodging` and the trip's data block has no lodging entry with a `place_id` or finite `lat`/`lng` (an already-located trip answers `how: already` with no Maps call). Intake does not call it: the confirmed lodging text reaches the step through the `research` (`new`) request the pack opens after confirmation — the same code path, no second entry point.
17. **One Maps call, pro tier.** A Maps link carrying `place_id:<id>` → one Place Details; otherwise one Text Search, page size 3, query = the lodging text with a trailing "N nights" removed + ", <destination>[, <country>]" (the destination bias). Counted on `MAPS_USAGE_LEDGER` like every other Maps call; `--maps live|fixture:<name>` as the other drivers.
18. **Acceptance rule.** The first result whose name shares at least one distinctive word with the owner's text (words of 3+ letters minus a small generic list — hotel, guesthouse, rooms, nights, lane, station, …) is taken; otherwise `no_match`. Text with no distinctive word at all is `no_name` and is not searched. Instruction-shaped text (the prefs kit's `injectionReasons`) is `instruction`, never sent to Google, `injection_suspect: true`. Any of these leaves the data block unlocated, writes `<out>/lodging.json` with `located: false` and a `line`, and `trip-research-record.mjs` appends that one line to the round's reply ("I couldn't place where you're staying — tell me the name and address, or send a Maps link."); plan-days then reports `lodging_missing` as before. The step always exits 0 on a decision (1 = trip not found, 2 = usage).
19. **What is written.** `lodging: [{ id: slugify(name), name, place_id, lat, lng, from: start_date, to: end_date + 1 day, address? }]` — one entry covering every night, `to` = check-out, as the trip schema and `plan-days` expect; the whole trip is validated against the schema before `saveTrip`. The `Staying:` Owner-notes line stays as the owner's words. The result's name and address come from Google's pro field mask, not from the owner's text.
20. **Dry runs stay mock-only.** `tools/tg-maps.mjs` `composedResponder` answers a `places:searchText` the pack fixture does not know by looking the query up against the fixture trip's lodging names (`fixtureLodgingPlace`), so the journey and integration runs locate the fixture lodging through the real step without a network call; a query naming nothing falls through to the kit's generic fixtures (which do not match, giving `no_match`). The trip-research examples' confirmed lodging was renamed to the fixture lodging name so the recorded `research` (`new`) request locates it. In the integration red team the lodging round runs on its own copy of the red-team repo, because its record step writes `places/` for the shared destination and would reshape the later replan check.
