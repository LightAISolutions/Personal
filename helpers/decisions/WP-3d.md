# WP-3d — decisions and defaults

Numbered so the coordinator and WP-4d can cite them. "Given" = fixed by the coordinator's binding decisions; the rest was chosen without asking, per the WP rules.

## Given (coordinator)
1. **Payload shapes as specified.** trip_facts kinds `dates|lodging|flight|booking|companions|other` (no synonyms); shortlist `v` const 1 and `kind` const optional, `decided` ≤ 200 slugs, `place_id`/`new` optional, `why_you` ≤ 160 (may be empty), `fit` 0–1, labels closed `verified|single source|conflicting|unverified`, `gem_line` ≤ 200, `gems_wanted`/`gems_shown` 0–8, ≤ 2 groups, ≤ 20 items, `n` 1-based; trip_facts `found` ≤ 40, text ≤ 200, start/end date or null, `missing` ≤ 10; plan_digest theme ≤ 80, legs `{from,to,mode,minutes,maps_url?}`, ≤ 20 warnings of ≤ 200, Later reason ≤ 300, Drive ids `^[A-Za-z0-9_-]{10,200}$` or null, ≤ 60 000 characters (semantic check); profile_summary text ≤ 1200, `dimensions_count` integer ≥ 0, `updated` ISO date-time; prefs_review = the prefs kit's actual output, ≤ 40 items; Place gem fields; LaterList `owner_choice` and `not_shown`; places_digest with the twelve listed fields, no Google fields, strict.
2. **`helper.json`**: the six types, `action_allowlist` empty.

## Chosen
3. **Trip status keeps `draft` for now.** Both fixture trips and the planner test world say `"draft"`, and WP-3d owns neither. The enum is the six new values plus `draft`, described as legacy. Request 1 moves the fixtures; then `draft` goes.
4. **"Saved by you" is a third named list, not "Next time".** "Next time" (code `owner`) already means "the owner moved it off a planned day". A shortlist choice is a different act, so the owner sees it separately. Reason text: "you kept this for later when choosing from the shortlist". `not_shown` gems go to "Gems not chosen".
5. **picks are the whole pool.** A candidate the owner did not pick is not planned and is put in no Later list: it was not chosen, it did not fail to fit. The plan check accepts such a place only when `plan.choices` exists and the place is still a `candidate`, so a plan without choices keeps the old rule (every non-rejected place scheduled or listed).
6. **`chosen` is an input status; the plan's statuses stay the Phase 3 ones.** The planner pools candidate, chosen and scheduled alike. In the output a scheduled pick is `scheduled`, a pick that did not fit goes to "Didn't fit" and becomes saved-for-later (picks are never silently dropped), and an unpicked pool place is back to `candidate`. The private repo may store `chosen` on a place between the shortlist and the plan; the planner reads it as "picked".
7. **A promoted place counts as picked.** `later.promote()` puts `scheduled_hint` on a candidate; with choices present that place joins `picks`, unless the same call names it in `later` or `skip`.
8. **Explicit vs recorded choices.** `planTrip` treats choices as explicit: a pick may bring back a saved-for-later or rejected place, `later`/`skip` override any status. On `replanDays`, `input.choices` is explicit; without it the recorded `plan.choices` only filter (they never resurrect or re-reject, because the places passed in already carry the statuses those choices produced). `choices: null` drops them.
9. **Keeping or skipping a place scheduled on a day not being re-planned is an error.** Silently leaving it on that day would contradict the owner; silently removing it would change a day the caller asked to keep. The message says which day to add.
10. **Bad choices throw** (unknown slugs listed, a slug in two lists, unknown keys, non-arrays). Duplicates inside one list are dropped: harmless and common when a list is built from taps.
11. **`plan.choices` = the effective lists, sorted**, and only when choices were given — a choice-less plan stays byte-identical to before (hashes in the status file).
12. **Shortlist `round` ≥ 0, `more` boolean or integer 0–1000.** The driver's format is not written yet; both readings ("there are more" / "N more") are accepted rather than guessed.
13. **Shortlist `n` is unique per group, a slug unique across groups.** The owner taps numbers inside a group message; the same place twice would be two answers for one place.
14. **prefs_review limits beyond the kit's**: `statement` ≤ 400, `value` ≤ 200, `held_back` ≤ 1000, button `data` must name its own item's `cid`. Generous enough for the kit's real output (tested), tight enough to catch a hand-edited payload.
15. **`profile_summary.updated` is checked as a real date.** V8's `Date.parse` accepts 2027-02-30, so the date part is checked on its own as well.
16. **`envelope.mjs` stays generic.** `--pack <name>` loads `packs/<name>/schemas/index.mjs` when it exists and calls its `validatePayload`; core types and packs without schemas are unaffected. `makeEnvelope` stays synchronous; the async check is `packPayloadErrors` and the CLI awaits it.
17. **`validatePayload` on an unknown type returns `ok: false, kind: null`** with a message listing the known types, instead of throwing: callers validate many envelopes in a loop.
18. **`profile_summary` = `{ text }` (WP-2f request), extras optional.** The prefs kit returns a plain-text summary of ≤ 1 200 characters; the payload carries it as is, so only `text` is required. `dimensions_count` and `updated` from the coordinator's first decision stay as optional fields (checked when present: `updated` must be a real date-time), so a driver that has them can still send them and nothing written for the first shape breaks.
19. **Gem fields spelled as WP-2g-engine's status file says.** `gem_score` is a number 0–100 (the coordinator's summary said integer; the module emits a number and its status file wins, per the coordinator). The other fields were already identical.
