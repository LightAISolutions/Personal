## 2. Request-kind contract (as implemented — what Phase 5's core emits)

The core writes `TourGuide/mailbox/to-brain/req_<id>.json` (`producer: "tour-guide-core"`, `type: "request"`, `payload: {kind, text, chat:{message_id, ts}, …}`) and fires the routine with `text` = `req_<id>`; `payload.text` is always the owner's words. Extra fields are all optional. Source of truth: the private repo's `skills/README.md` ("Tour Guide conventions").

| `kind` | Skill | Extra payload fields | Reply |
|---|---|---|---|
| `research` | `trip-research` | `trip` (slug) · `scope`: `new` (default) \| `more` \| `intake` · `like` (a place slug: "more like X") · `decided` (slugs the owner already picked, saved or skipped in earlier rounds; `more` never repeats them) · `destination`, `start_date`, `end_date`, `lodging`, `booked` (the owner's confirmed intake facts, as the owner's words) | `intake`: one line per fact found in Calendar, Gmail and Drive (confirm / edit / reject) plus what is missing (`trip_facts` once registered); `new` / `more`: one shortlist round (activities, then food; numbered, slugs in backticks, labels not prose) and the same round as `shortlist-<run_id>.json` in the trip's Drive folder (`shortlist` once registered) |
| `plan` | `plan-days` | `trip` · `picks` (only these are planned; the rest keep their status) · `later` (→ `saved-for-later`, "Next time" with reason `owner_choice`) · `skip` (→ `rejected`) · `deliverables` (default `["plan"]`; `plan`, `notes`, `brochure` — the latter two run place-notes and brochure-build in the same run, in that order) · `seed` · `allow_over_budget` (only from the owner's words) · `show_google_content` (standing answer, remembered in `profile_overrides`) | one `reply`: day list, Later reasons, every warning, the notes count, the brochure's Drive path with the HTML and PDF file ids (` · ids html:<id> pdf:<id>` on the Brochure line, so the core can send the PDF); the Plan JSON on Drive |
| `replan` | `plan-days` | `trip` · `dates` (required) · `promote` (slugs onto the one date given) · `demote` (slugs out of the plan) · `reason` | the same, for those dates (a demoted place's days are re-planned too) |
| `notes` | `place-notes` | `trip` · `places` (default: every scheduled or saved place without a current note) | `reply` with the count written and the could-not-source list |
| `brochure` | `brochure-build` | `trip` · `build_id` (default: latest) · `show_google_content` | `reply` with the Drive link(s) |
| `prefs` | `prefs-build` | `window_days` (default 365, cap 730) · `interview` (`{version:1, answers:[{qid, dimension, value, polarity, kind: pick\|text}]}`) | `notice` with `in_reply_to`: picks saved, candidates to confirm / edit / reject by `cid` (`prefs_review` once registered) |
| `message`, `ask` | `chat` | — (the core's own kinds, SPEC §3) | `reply`; a plan change becomes a fenced `{"handoff": {kind, …fields of that kind}}` block inside `reply.text` (`chat-check.mjs` enforces the kinds-table fields; `prefs` is never a hand-off) |

Shared rules: a skill fired for a kind it does not own appends one `log/` line and ends; a missing `trip` is resolved from `payload.text` against `trips/` (slug or title, then a destination whose words all appear), else the only trip not `done`, else the reply asks which trip (the one question a skill asks). Every `reply` fits one Telegram message: ≤ 4000 characters (the envelope's limit; `TG_MAX_CHARS` 4096 after HTML escaping) and ≤ 40 lines. Dedupe keys: `chat-<id>`, `prefs-review-<batch_id>`, `trip-check-<local date>`.

## 4. Drive and memory layout

- **Drive** (the one connector write a routine makes is `create_file`, `disableConversionToGoogleType: true`): `TourGuide/trips/<slug>/dossier.md`, `shortlist-<run_id>.json`, `plan-<build_id>.json`, `brochure-<build_id>.html` and `.pdf`. `TourGuide/mailbox/{to-brain,from-brain,archive}` belongs to the core.
- **`trips/<slug>.md`**: rendered view (header with the real status, lodging, numbered Candidates table with slugs / statuses / minutes, latest build's day summaries, Later lists, research runs, open questions) → `## Owner notes` (verbatim, the owner's words only) → `<!-- tour-guide:data v1 -->` + one fenced JSON block `{ trip, places, estimates, calibration, later, builds, profile_overrides, research, locations }` in the pack schemas' shapes. `builds[]` = `{ build_id, built_on, verified_on, drive, days:[{date, theme, summary, warnings}] }`, never the Plan; `research[]` = `{ run_id, round, …, shortlist }`; `locations` per decision 14.
- **`places/<slug>.md`**: the PlaceNote rendered (why you, what to do, what to skip, best time, tickets, accessibility, pairings, food, sources) → `## Owner notes` → data block `{ place, note }`; one file per place shared by every trip; `slug` = the Place `id`.
- **`profile/travel-profile.md`** (+ `travel-profile.decisions.json`): written only by the prefs kit; `profile/` is the memory dir with the kit's interview picks and reviewed connector evidence.
- **`quarantine/`**: `<date>-<slug>.md` (research passages), `<date>-<slug>-intake.md`, `<date>-notes-<slug>.md`, `<date>-chat-<slug>.md`, `prefs/` (held prefs notes) — everything derived from untrusted content, with its source named.
- **`log/`**: `YYYY-MM-DD.md` one line per run (class or silence reason, never the owner's words); `maps-usage-ledger.json` (the Maps kit's SKU ledger, committed with the run, merged by the driver of decision 13).
- Google content never lands in memory (place ids and ≤ 30-day coordinates only); raw page text never enters `trips/` or `places/`.

## 7. What each skill needs from the core (Phase 4b WP-1b and Phase 5)

1. **Fire and request**: `text` = `req_<id>` only; `req_<id>.json` with `payload.kind` and the fields of §2; `state.json` with `tz`, `requests_open` and `wake_url`. The core removes an answered or expired request from `requests_open` — `chat` reads absence as "already answered" and reads nothing else on a bad fire text.
2. **`plan` delivery**: the core sends the brochure PDF to the chat from the Drive ids on the reply's Brochure line (` · ids html:<id> pdf:<id>`) with `tgSendDocument` (WP-1b); until a typed envelope carries them, the ids ride in the reply text.
3. **`/plan` journey**: intake → the core collects confirm / edit / reject per fact line and sends the confirmed values back as `start_date`, `end_date`, `lodging`, `booked` on the next `research` request (the owner's words); shortlist → the core turns the owner's choices into `plan` `picks` / `later` / `skip` (the reply's pick line is already in that form: `/plan <slug> picks: a, b later: c skip: d`) and passes earlier rounds as `decided` on `more`; `deliverables` `["plan","notes","brochure"]` for the full journey.
4. **`prefs`**: the `/interview` flow supplies `payload.interview`; the owner's `confirm|edit|reject <cid>` answers (`pf:<cid>:y|e|n` callbacks) become a `prefs_decisions` request for the kit's `apply`.
5. **Hand-offs**: the core must strip or parse the fenced `{"handoff": …}` block in a `chat` reply and, after the owner confirms, write a `req_<id>.json` of that kind (WP-4c R4). `/later` promotion and a `trip-check` notice both end in a `replan` request for the affected dates.
6. **Status**: nothing in the core writes the repo; the trip's status moves only through the skills (`intake` → `researched` → `planned` → `delivered`). `choosing` is in the vocabulary for the core's own flow state (§8 item 6).
