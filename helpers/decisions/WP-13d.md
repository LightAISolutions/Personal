# WP-13d — decisions (Scout engine: been before, city days, one grammar, the vegetarian flag, own names)

Brief: `helpers/prompts/TG-PHASE-13.md` "WP-13d". Contract as built: `helpers/decisions/TG-SCOUT.md` §9.

1. **`known` takes an array or a Set** of place ids (non-strings in an array are ignored). The label only; the score is unchanged, so a known place is neither pushed down nor up. Both `rankScout` and `scoutPayload` accept it, so the driver may pass it at either step.
2. **`city_dates` counts as given whenever it is an array**, even an empty one (the owner is in that city on no trip day → no closed screen, no penalty, no hours on the board). Invalid dates are dropped, the rest sorted and de-duplicated. Reason: an explicit "no day there" must not fall back to the whole trip, which is the fault itself. A driver that does not know the city's days omits the field.
3. **Grouped hours rows on every board**, with or without `city_dates`: the brief's "consecutive dates with the same hours share a row" is applied to the trip's dates too, because without the seven-date cap an ungrouped fourteen-day row is long. Only calendar-consecutive dates merge (a gap starts a new row). `tripHours` stays per date (the compare table counts per date); the new `hoursRows` groups. Range labels: "Wed 5 – Sat 8 Mar", across months "Sun 30 Mar – Tue 1 Apr".
4. **Board wording.** `closed_on_trip` reads "closed on every day you are there" when `city_dates` is given, else "closed on every trip day" as before; `diet_unproven` now reads "vegetarian not confirmed" (the brief's words, and the core's chat already says so).
5. **The grammar follows the core's separator order** (last " in ", first " near ", first "@", first ","), not the engine's old "earliest separator", so the two agree on every case the core handles (checked against `tgScoutParse` for the fixture table; `core_same` marks them). Where they disagree it is only the engine's cleaning (`/scout` prefix, trailing `?`) and one extension: "<what> near <area> in <city>" splits the area out of `what` (the core keeps "ramen near the ferry pier" as the what). `where` keeps the place as written, and is "<area>, <city>" for that extension.
6. **"<what> near <area>" without a comma** gives `area` = the place and `city` = '' (the caller falls back to the trip's destination or its stays and day towns); a single name after "near" is more often a quarter or a landmark than a city.
7. **"<what> in <a>, <b>" names the city alone** (`city` = "<a>, <b>"), as the brief's rule says; only "near" splits an area. "oysters in Gullhaven, Wren Coast" must not become city "Wren Coast". The private driver matches the city against the trip's stays and day towns.
8. **The hidden-stock rule is any non-blank string** (≤ 200 kept, whitespace collapsed); anything else is no rule. It only matters for a vegetarian diet (Google's flag never counted for other diets). The café exception is the query, not the place: a topic carrying a `CAFE_WORDS` word (two-word ones such as "ice cream" included, the same word test as `guessGroup`) — the brief's "a pick whose topic is a café word". Exported as `isCafeTopic`, `dietRule`, `googleVegCounts`.
9. **Own names come from the judgment's `name`.** `ownName` strips control and bidi/zero-width characters, collapses whitespace and clips to 120 (with an ellipsis, as other clipped text). A blank result is no own name. The item's `name` (ranking, payload, left-out list) is the own name when given, else Google's; the item also carries `own_name` (null without). The slug of a new place follows the item's name, so an own name gives an own slug.
10. **An existing place without an own name is still updated** (tags, the `scouted` history entry), keeping its stored name: nothing of Google's is written, and a "been before" place — exactly the ones already in `places/` — must keep its scouting history. Only a *new* place without an own name returns `{ place: null, reason: 'no_own_name' }` (exactly those two keys). An own name passed for an existing place does not overwrite its stored name (the owner may have set it; the old Google-named files are the private data pass's job).
11. **Engine tests updated for the new shapes** (both are this WP's Scout engine tests): `pack_tour-guide_scout.test.js` (the parse result gains `city`/`area` — fault 11; a new place needs `own_name` — B9; the parse cases now use invented names) and `pack_tour-guide_scout_redteam.test.js` (the hostile place test passes a hostile own name and checks it is cleaned and clipped — B9). No assertion was weakened.
12. **Reproduced first.** All six new tests in `pack_tour-guide_p13d_scout.test.js` were run against the unchanged engine (the scout directory restored from `HEAD`) and all six failed; then against the fix, all pass.
