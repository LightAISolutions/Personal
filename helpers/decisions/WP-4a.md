# WP-4a — trip-research, plan-days: decisions

Every default these two skills picked, and why. Shared design points (`skills/README.md` Tour Guide conventions) are followed as written and not repeated here.

## Shared
1. **Written by the coordinator, on the session branch.** TG-PHASE-4 offered a worktree or an `hb-builder-fable` agent; the two skills sit on the engine's contract that the coordinator had just read end to end, and the two builder agents ran in parallel anyway, so writing them directly cost less than briefing a third agent. Recorded here as the prompt asks.
2. **Extra `## Procedure` section** between Inputs and Output (the same role as WP-4b's `## Steps`): a routine needs the order of tool calls and the exact driver invocations.
3. **Drivers write the payloads**; findings (a missing trip, no lodging, an unknown slug, a blown budget) are written as `reply.json` with exit 1, so the routine never composes an error message itself and every question the owner can be asked is a tested string.
4. **Trip resolution** is the shared rule (request `trip`, else text against `trips/`, else the single open trip, else ask); the start driver implements it so both skills resolve the same way.

## trip-research
5. **Two drivers, one brief in between.** `start` turns the request into a `brief.json` (what to look for, what already exists, how many to find, budgets, file paths); the routine researches; `record` turns `candidates.json` into memory. The research itself is the only part a model must do, so it is the only part not scripted — and a Phase 5 `/plan` flow can call the same two steps.
6. **Draft trips have no lodging.** The Trip schema requires `lodging`; research precedes booking. A new trip is written with `lodging: []` and `status: draft`, validated against a placeholder lodging only for the schema check; `plan-days` refuses it with `lodging_missing` until the owner says where they stay. `modes` default `[<mode>, 'WALK']`, day 09:00–18:00, pace from the profile.
7. **Slug** `slugify("<destination> <YYYY-MM>")` of the start month; title from the request or "N days in <destination>".
8. **Refs only, never URLs.** Candidate mentions and sources are research-kit refs (`L00n`, `L00n.k`) resolved against the run ledger; a URL typed by the model is not accepted. A ref whose page is `injection_suspect` is dropped from durations and citations (the kit's rule), and the count of ignored pages is stated in the reply.
9. **Every place id is verified** with one Place Details call at the pro tier (name and business status) before it enters memory; a failure drops the candidate and the reply says so. Google's name and status are used for the check and the reply, not stored.
10. **`wanted`** = 15 for a new trip, 6 for `more`; the estimator's categories are the only ones accepted (`museum`, `viewpoint`, `market`, `hike`, `park`, `church`, `neighbourhood`, `restaurant`, `cafe`, `shop`, `other`).
11. **Dossier** = the trip's candidates with their estimates, sources (titles and domains, not page text), facts labelled by freshness, and the could-not-verify list — a Drive file the owner can read, never an envelope. Passages the model relied on go to `quarantine/<date>-<slug>.md` only.
12. **Reply** = numbered list with slug, category, ~minutes, confidence, `why_fit`, ⚠ for non-operational places, the could-not-verify list, the ignored-page count, and a ready-to-send `/plan … picks:` line (plus "I still need where you are staying" for a draft trip).

## plan-days
13. **Enterprise tier** for the build's snapshots: the planner needs opening hours and the prompt's "Essentials cost" tier carries none. Snapshots live only in the scratch store and are purged in a `finally`.
14. **`picks` = the planner's pool.** Picked places become candidates; unpicked ones keep their status and stay out of this build (a previously scheduled but unpicked place goes back to `candidate`); saved-for-later places are always carried so their list survives.
15. **`replan` takes `promote` and `demote`.** Promotion puts a Later place on the one date given (the pack's `later/promote`); demotion takes a place out with the owner's reason and re-plans every day it was on (the days `later/demote` reports are added to `dates`). The prior Plan JSON comes from Drive (`plan_missing` otherwise) and must name the same trip.
16. **Budget.** `PlanBudgetError` becomes a `budget` finding whose reply states the estimate and the ceiling; `--allow-over-budget` is passed only when the owner's own words in this request say so.
17. **Build id** `build-<YYYYMMDDHHMM>` (UTC) unless given; Drive path `TourGuide/trips/<slug>/plan-<build_id>.json`; `builds[]` stores the day summaries, not the Plan.
18. **Trip status** becomes `planned` after a successful build (a `done` trip stays `done`).
19. **`show_google_content`** is recorded in the trip's `profile_overrides` when the request carries it, so brochure-build finds the owner's standing answer there (WP-4b request 3).
20. **Reply** = per day: theme, stops with arrive–depart, minutes, confidence and 🎟 for booked; lunch; back at lodging with the day's route link; ⚠ warnings; ℹ places with unknown hours; "Not in the plan" with each Later reason; snapshot failures; the Drive path and `verified_on`.

## Phase 4 delta (TG-PHASE-4-DELTA §3, applied by the coordinator on the session branch)
21. **Trip statuses** `intake · researched · choosing · planned · delivered · done` live in `tools/tg-memory.mjs` (`TRIP_STATUSES`); the pinned Trip schema's enum is still `draft | planned | done`, so every driver validates through `schemaTrip()` (intake / researched / choosing → draft, delivered → planned). Phase 4b widens the enum and `schemaTrip` becomes the identity. The prose header shows the real status.
22. **`plan` later / skip** are build-time inputs of `plan-days-build.mjs` (`--later`, `--skip`; kind `plan` only — a replan uses promote / demote). Later → status `saved-for-later`; the planner's "Next time" item for it gets the reason text `owner_choice — saved by you for later` (the LaterList `code` enum has no `owner_choice`, so the reason string carries the word; `code` stays `owner`). Skip → status `rejected`. A slug in two lists is a `conflicting_choice` finding.
23. **Chaining** is a separate run driver, `plan-days-run.mjs`, that spawns the three skills' own drivers (`plan-days-build`, `place-notes-todo` / `place-notes-write`, `brochure-build-render`) and keeps `<out>/run-state.json`, so the notes stage can pause for the routine's research (`pending: "notes"`) and resume with `--notes` without rebuilding the plan. The brochure stage sets the trip's status to `delivered`. Drive file ids are added after the fact with `--attach html=…,pdf=…` (the driver never calls Drive). One reply ≤ 40 lines and ≤ `TG_MAX_CHARS` − 96 (4000 wins): days collapse to one line each when the full form would not fit.
24. **Shortlist** is built by `trip-research-record.mjs` from the round's new candidates only (decided slugs and places already on the trip are left out): groups `activities` / `food` (restaurant, cafe), caps 8 / 6 (`--activities`, `--food`), `fit` = priority (0.9 / 0.6 / 0.35) ± the profile's interest in the category, `labels` from the estimate's confidence, `maps_url` = `https://www.google.com/maps/place/?q=place_id:<id>`, `area` from the routine's candidate (`area`, its own words) else the destination, `run_id` = the research-kit run id's first 8 hex characters, `round` = the trip's research-entry count. It is written to `<out>/shortlist-<run_id>.json`, named in the trip's research entry and kept in the Drive folder; the prose reply is the same round.
25. **Intake** is a third driver, `trip-research-intake.mjs`: the routine reads the connectors and writes `facts.json` in its own words; the driver validates kinds and sources, drops instruction-shaped facts from the reply (kept in quarantine as suspect), writes `quarantine/<date>-<slug>-intake.md`, the `trip_facts` payload and the reply. A trip created at intake may have no dates (slug = the destination); `trip-research-start.mjs` fills them from the next request's confirmed `start_date` / `end_date`. The lodging itself still enters through plan-days' question (the owner's words), never from a mail.
26. **`decided`** flows `request → trip-research-start --decided → brief.decided → trip-research-record --decided`; `--wanted` for `more` is 8 (one activities round).
