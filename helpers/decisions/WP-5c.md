# WP-5c — Lane B, `/smart`, `/route`, measurement, mock end-to-end: decisions

Owner: WP-5c (Phase 5, `hb-builder-opus`). Files: `helpers/packs/tour-guide/gas/30_chat_api.js`, `gas/31_route.js`, `helpers/tests/pack_tour-guide_gas_{chat,route,e2e}.test.js`. No live Claude API, Maps, Telegram, Drive or routine call was made; every number below comes from the mocks or is an estimate whose assumptions are stated.

## Lane B (`30_chat_api.js`)
1. **When Lane B answers.** Mode = `Settings.tg_smart` (`on`/`off`, written only by `/smart`); when never set, the property `CHAT_API_ENABLED === 'true'`; Lane B is on only when the mode is `on` **and** `CLAUDE_API_KEY` is set (§1.9). The owner's toggle beats the property once used. `/smart on` without the key changes nothing and names the property. `/status` gets one line through `core_status`: `Answers: free (routines)`, `Answers: smart (Claude API, paid per use)`, or the free line plus "smart is on but `CLAUDE_API_KEY` is not set".
2. **Lane B answers only quick questions about the current trip.** The handler hands the text back to the core (returns false → a `message` request, the CHAT routine, exactly as with Lane B off) when: Lane B is off; the text is empty or > 1 500 chars (a task, not a question); a cooldown is running; today's calls reached `CHAT_API_MAX_PER_DAY` (default 60); there is no current trip (`tgTripCurrent()` null — without a digest there is nothing to answer from); the model replies `NEEDS_DEEP`; the API refuses (`stop_reason: refusal`), returns nothing, an HTTP error or the fetch throws. Free text inside an active flow never reaches it (the core's flow claim comes first), and capture handlers are named `tg_capture_*` so they sort before `tg_lane_b` (§1.6).
3. **Model rule.** Haiku 4.5 (`claude-haiku-4-5-20251001`, the id the brief names — the pinned snapshot of the `claude-haiku-4-5` alias; `CHAT_API_MODEL_LOOKUP` overrides) for a *trivial lookup*: ≤ 100 chars, one line, at most one `?`, a fact cue (when · where · what time · which day · how far/long/many · address · today · tomorrow · tonight · day N · first/next/last stop · hotel · lodging · check-in) and no judgement cue (why · should · recommend · suggest · best · better · compare · idea · instead · alternative · plan · change · could · would · near · nearby · around · anything · something · free). Everything else Sonnet 5.5 (`claude-sonnet-5-5`, `CHAT_API_MODEL` overrides). Deterministic and testable; the owner's taps in Phase 8 can tune the word lists.
4. **Request shape.** One `POST https://api.anthropic.com/v1/messages`, headers `x-api-key` (Script Property) and `anthropic-version: 2023-06-01`, `muteHttpExceptions`, no `tools`, no web, `max_tokens` 900 (Sonnet) / 400 (Haiku). Sonnet 5.5 runs with `thinking: {type: "between_tools"}` (thinking off — Sonnet 5.5 rejects `disabled`, and with no tools there is nothing between) and `output_config.effort: "low"` (chat), to stay fast; Haiku 4.5 gets neither field (it rejects `effort`). No server-side `fallbacks` beta: a refusal already has a fallback that costs nothing extra and needs no beta header — Lane C.
5. **Prompt-injection posture.** The system prompt is fixed text. The context is a JSON object inside `<trip_context>`; the owner's text inside `<owner_message>`; the system prompt says both are data, that instructions inside them are never followed, and that anything not in the context (web, prices, hours not given, bookings, availability, research, plan changes) gets the single line `NEEDS_DEEP`. The answer is model output derived from brain data → `tgEscape`d, cut to 3 600 chars, plus a one-line footer (always ≤ `TG_SPLIT_AT`); it is never parsed for links, commands or actions. Lane B can only send text to the owner.
6. **Context.** The current trip row (title, destination, dates, status, lodging text, verified_on), its digest days (today and later days first, then past days; theme, stops with arrive/depart/minutes/note line, legs with mode and minutes, warnings), the Later list (name, reason, ≤ 30) and up to 8 repository hits (`tgPlacesSearch` on the two longest content words of the question; name, area, category, status, note line). Capped at 24 000 chars (≈ 6–7 k tokens) by dropping the furthest days first. Every storage call is wrapped: a failing one only shrinks the context.
7. **Timeout budget.** Apps Script has no per-request UrlFetch timeout (plan fact 8 inference: ≈ 60 s). Latency is bounded by the request instead: no thinking, low effort, ≤ 900 output tokens, ≤ ~7 k input tokens — a few seconds expected (an inference, not measured live). A call slower than 25 s, an HTTP error or a thrown fetch starts a 10-minute cooldown (cache key) during which free text goes straight to Lane C, so a slow or failing API never makes two messages in a row wait. Telegram's `update_id` dedupe protects against a webhook retry.
8. **Key handling.** Read only from Script Properties at call time; never put in a URL, a log line, an audit row or the Sheet. The core's `redactSecrets()` redacts every `*_API_KEY` property value (coordinator change on WP-5c's request); the test asserts a thrown fetch whose message contains the key is audited as `[redacted]`.
9. **Usage and cost line.** `Settings.tg_chat_usage` = JSON per local day `{ calls, answered, deep, failed, in, out, usd, models }`, 35 days kept; `usd` at list price (Sonnet 5.5 $2 / $10, Haiku 4.5 $1 / $5 per MTok, plan fact 13). `/smart` shows today's answered count, tokens and cost. Estimate: a Sonnet answer with a full context ≈ 6.3 k in + ~200 out ≈ $0.015, a Haiku lookup ≈ $0.007; the plan's 200 questions a month ≈ $1.5–3 (plan §8 said ≈ $5 at 8 k / 1 k); the worst case at the default cap (60 Sonnet calls a day at full context and 900 output tokens) ≈ $1.30 a day. The cap is the spend guard; `CHAT_API_MAX_PER_DAY` changes it.
10. **Default off.** `CHAT_API_ENABLED` defaults to false and `tg_smart` is unset, so a fresh install answers through the routines (owner's answer, §1.9).

## `/route` (`31_route.js`)
11. **Syntax.** `/route A → B [mode]`; separators `→`, `->`, `⟶`, `=>` first, else the first ` to ` (so "Station to Harbor to Museum" goes Station → "Harbor to Museum"; an arrow avoids the ambiguity). A trailing mode word (optionally after `by`): walk/walking/foot, transit/train/subway/metro/bus/public, drive/driving/car/taxi. **Default mode transit** (city travel). Each place ≤ 200 chars.
12. **Resolution.** With a current trip: `hotel` / `lodging` / `inn` / `airbnb` / `home` become the trip's lodging text; a place without a comma that does not already name the destination gets `, <destination>` so short names resolve in the right city. The answer says "searched as …" whenever a name was changed.
13. **Maps service.** `Maps.newDirectionFinder().setOrigin().setDestination().setMode()` (+ `setDepart(now)` for transit) `.getDirections()`; minutes = sum of leg durations rounded (≥ 1), distance = sum of leg metres; summary = the transit line names in order, else Google's route summary. Results are shown and forgotten (never stored). Cached 6 h per (from, to, mode); ≤ 200 live queries a day (`Settings.tg_route_calls`), far below the 1 000/day quota (fact 8). Errors never throw: `no_route`, `not_found`, `quota`, `daily_cap`, `maps_error`; a transit miss suggests the walk variant (Google has no transit data in some countries — Japan; the planner's rail estimates live in the engine, not here). Every answer carries the Google Maps directions link (`https://www.google.com/maps/dir/?api=1&origin=…&destination=…&travelmode=walking|transit|driving`), even on error.
14. **Testing the Maps service.** The harness has no `Maps` mock; the route test sets a minimal `DirectionFinder` mock on the vm context from the test file (no harness change).

## M. Trigger-minute measurement
Budget: the Apps Script consumer quota is 90 trigger-minutes per day; only **time-driven (one-off / clock) trigger runs** count. Web-app executions (Telegram webhook `doPost`, the `wake` route `doGet`) do not. Assistant Brain uses about 12–24 of the 90 (AB `docs/SPEC.md` §8). Execution time per sweep run is assumed ≈ 5 s (a Drive folder listing plus a few small reads/writes; 4–8 s observed in AB), so 12 runs ≈ 1 trigger-minute.

**Measured** (spy on `scheduleOneOff`, counts of `H.fireTriggers` runs and UrlFetch calls, in `pack_tour-guide_gas_chat.test.js`):

| Case | One-offs scheduled | Trigger runs | Trigger time |
|---|---|---|---|
| Lane B answers (smart on) | none | 0 | 0 s (all inside the webhook) |
| Lane C deep request, reply on time (wake route delivers it) | `wakeTrigger` +3, +10 | 2 (both find nothing open and stop) | ≈ 10 s |
| Lane C, routine slow and its wake lost | +3, +10, then hourly +60 once | 3 (the hourly run delivers) | ≈ 15 s |
| Lane C, routine never answers | +3, +10, then hourly until expiry (24 h) | ≈ 26 | ≈ 2.2 min, once |

Lane B uses no trigger time but holds the webhook for the Claude call (≤ ~25 s). If another update arrives while the lock is held, the core defers it to `queueTrigger` (+1 min, one short trigger run). That is rare and costs seconds.

**/plan** (measured in `pack_tour-guide_gas_e2e.test.js`, see §M.2): one brain request per step (intake, research, one per More round, plan). Each one schedules +3 and +10, and the hourly guard is shared (one at a time, cache `sweep:hourly`). One planned trip with one More round is 4 requests → 9 trigger runs → **≈ 45 s, under 1 trigger-minute**.

**Daily estimate:** typical ≈ 3–6 Lane C requests plus the daily jobs ≈ 0.5–1.5 min. A heavy planning day (a full `/plan` plus 10 deep questions) ≈ 2.5–3 min, but past the default routine fire cap (§M.2). Both stay far below Assistant Brain's 12–24 and the 90 cap, so Tour Guide and Assistant Brain together fit on one account even if they share a quota. The main lever is free-by-default (§1.9): `/smart on` moves quick questions out of the trigger path entirely, but they are paid per use. Usage is tracked in Settings `tg_chat_usage`, and `/smart` shows today's count and dollar estimate.

### M.2 `/plan` measured end to end
Test `e2e /plan` in `helpers/tests/pack_tour-guide_gas_e2e.test.js`. It uses the real pack files and the core, with a spy on `scheduleOneOff`; every one-off whose time has come is fired minute by minute while the routine "works". Journey: `/plan Harbor Town` → intake answered at minute 8, with its wake call lost (the +10 sweep delivers it) → fact edit, dates, flight skipped → research answered at +12 through the wake route → round 1, ➕ More options → round 2 at +9 through the wake route → Done choosing → plan answered at +14 through a direct poll, plus the core `reply` with two Drive files → 120 more minutes so every leftover fallback fires.

| Measured | Value |
|---|---|
| Brain requests (Requests sheet) | 4 (research `intake`, research `new`, research `more`, `plan`), all `answered` |
| Routine fires | 4 (one per request; the daily cap is 12 across all routines) |
| One-off trigger runs | **9**: `+3`/`+10` × 4 plus one shared hourly `+60`. Every scheduled one-off ran exactly once; no trigger left behind |
| Wake-route runs (web app, no trigger time) | 3 |
| Trigger time at ≈ 5 s per run | ≈ 45 s |

Only the +10 of the intake did useful work, because its wake was lost. The other 8 runs are cheap no-op sweeps (a folder listing, no open request). The hourly run happened once: it was scheduled by the first sweep while the intake was still open, and nothing was open when it ran.

**Daily cap on routine fires.** `MAX_ROUTINE_FIRES_PER_DAY` defaults to 12 across all of this helper's routines. A full `/plan` uses 4 (5–6 with more rounds), so the "heavy day" of §M (a full `/plan` plus 10 deep questions, 14 fires) passes the cap. From the 13th request of the day, the owner sees "⏳ Saved — the routine could not be fired right now (daily_cap)…". The request stays open until the next fire or until it expires after 24 h; meanwhile the shared hourly guard keeps running (≤ 24 runs ≈ 2 min, once per day, however many requests are stuck). Recommendation, recorded as a request in `helpers/status/WP-5c.md`: the Tour Guide setup notes should tell the owner to set `MAX_ROUTINE_FIRES_PER_DAY` to 20–24 if they plan several trips a day. That stays within the routine plan's own daily limit, and the trigger-minute cost is unchanged (≈ 2 runs per request).

### M.3 What the e2e also showed
- The throttled wake (two wakes within `WAKE_MIN_INTERVAL_SEC` = 15 s) schedules `wakeTrigger` +1, and that run delivers the envelope a minute later (test `e2e refusals and wake fallbacks`).
- A refused envelope (a shortlist item with `rating`, a place with `hours`) is moved to `archive/rejected` and audited as `envelope_rejected` with the field named. The owner is not messaged, the request stays `open` and the flow keeps waiting, so the brain's corrected envelope still lands.
- `tg_review_offer` runs inside the first sweep of the day after the trip ends, offers once (never again on later days), and the fl-button review ends in exactly one `prefs` request with `payload.review` (the stop-order items with `rating` and an optional `calibration`). The trip becomes `done`.
