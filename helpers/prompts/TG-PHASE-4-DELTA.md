## 1. What changed, in one paragraph
The owner's end product is a **Telegram chatbot** that opens with an **extensive preference interview** (food, activities, heat and cold tolerance, pace, budget, mobility, companions and more) and then takes commands such as **`/plan <destination>`**: the bot reads what the owner's connectors already know about that trip, researches current options on the web, **shortlists activities and food for the owner to choose from**, and turns the choices into day plans, place notes and the brochure, which it **sends to the chat as a PDF**. The plan now has a **Phase 4b** (gap closure, Fable 5.1 · high) that runs after Phase 4 and before Phase 5; it adds the core "flows" primitive and `tgSendDocument`, the interview block of the prefs kit, the engine's choice handling, the pack's envelope types, and the matching skill deltas in the private repo. Phase 5 (Opus 5.5 · high) then builds the chatbot pack around the `/plan` journey and `/interview`. Nothing you have built is redone.

## 3. Additions that are cheap now and expensive later — do these inside Phase 4
1. **`plan` carries the owner's choices and the deliverables.** Keep `picks`. Add three optional fields: `later` (place slugs the owner saved for later → status `saved-for-later`, Later-list reason `owner_choice`), `skip` (slugs the owner rejected → status `rejected`) and `deliverables` (array, default `["plan"]`; values `plan`, `notes`, `brochure`). When `deliverables` names `notes` or `brochure`, **`plan-days` runs the `place-notes` and `brochure-build` procedures in the same run** after the plan, in that order, so one routine fire produces the whole result, and its single `reply` carries the day list, the Later reasons, every warning and the brochure's Drive link (and the Drive file ids of the HTML and PDF, so the core can send the PDF). Make the three skills' drivers callable from one driver (`plan-days-run.mjs --deliverables plan,notes,brochure`); if the chaining itself does not fit in Phase 4, leave the drivers callable and write "chained by Phase 4b" in `plan-days`'s SKILL.md — the field names are what must not change later.
2. **`trip-research` writes a structured shortlist, not only prose.** Beside the numbered-list `reply` text, the driver writes a `shortlist` payload to `--out` with this shape (Phase 4b registers it as the pack envelope type `shortlist`; until then the skill sends the prose `reply` and keeps the JSON in the Drive dossier folder as `shortlist-<run_id>.json`):
   `{ "v": 1, "kind": "shortlist", "trip": "<slug>", "run_id": "<8 chars>", "round": 1, "groups": [ { "id": "activities" | "food", "items": [ { "n": 1, "slug": "...", "name": "...", "why_you": "≤ 160 chars, from the profile", "fit": 0.0–1.0, "est_minutes": 90, "area": "neighbourhood or day cluster", "maps_url": "https://www.google.com/maps/...", "labels": ["verified" | "single source" | "conflicting" | "unverified", ...] } ] } ], "more": true | false }`
   Defaults: 8 activities and 6 food items per round, ordered by `fit`; `scope: "more"` on a later `research` request adds a round without repeating a slug the owner already decided on (`picks`, `later`, `skip` of earlier rounds arrive in `payload.decided`). Every `name`, `why_you` and `area` is the skill's own wording; no page text, no review quotes.
3. **`research` learns an `intake` scope.** `scope: "intake"` means: before any web research, read the connectors the routine enables for what the owner already has for this destination — Calendar events and Gmail confirmations in a plausible window, Drive documents naming the destination — and answer with the facts found (dates, lodging, flights, booked tours, companions), each as one line the owner can confirm, edit or reject, plus which facts are missing (`dates`, `lodging`). Phase 4b registers the pack type `trip_facts` for this; until then it is a `reply`. Facts found in mail or invites are untrusted content: they go to `quarantine/<date>-<slug>-intake.md`, never straight into `trips/<slug>.md`; the confirmed values come back on the next `research` request (`start_date`, `end_date`, `lodging`, `booked`) as the owner's words. Create `trips/<slug>.md` at intake with status `intake`.
4. **Trip status vocabulary** (write it through `tools/tg-memory.mjs` now; Phase 4b widens the schema enum if it is closed): `intake · researched · choosing · planned · delivered · done`. `trip-research` sets `researched`, `plan-days` sets `planned` after the plan and `delivered` after the brochure.
5. **`prefs-build` accepts interview answers.** On the `prefs` kind, if `payload.interview` is present (`{ "version": 1, "answers": [ { "qid": "...", "dimension": "<vocab id>", "value": "...", "polarity": "+" | "-", "kind": "pick" | "text" } ] }`), the owner's **picks** are confirmed preferences — ingest them as `source_kind: "owner-chat"` evidence (`source_ref` `interview:<qid>`) and apply a decisions document (`source: "owner"`, `via: "telegram"`, one `confirm` per pick) in the same run; **text** answers become held candidates that go out for review like connector evidence. Without `payload.interview`, behaviour is unchanged. Phase 4b adds the prefs kit's `interview` command so this is one call; in Phase 4 write the two-step form (ingest → review → decisions → apply) in the SKILL.md and leave a `TODO(4b)` where the single command replaces it. The profile path is the one you chose in default 1; Phase 4b extends the vocabulary (climate tolerance and more) in `Personal`, which reaches you through the next pin.
6. **Reply size.** `shortlist` rounds and plan replies must fit one Telegram message each (`TG_MAX_CHARS` 4096 after HTML escaping): ≤ 40 lines, slugs in backticks, labels not prose.
