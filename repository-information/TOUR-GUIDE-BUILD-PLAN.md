## 1. The rule that shapes everything: this repo is public

`LightAISolutions/Personal` is public and so is its GitHub Pages site. `PERSONAL-ASSISTANT-ROADMAP.md` §3.11 already sets the rule: generic code may live here; personal data, persona and prompt files, memory and secrets may not. The build therefore splits into three homes, and the split is enforced by a CI check (Phase 1), not just remembered.

| Lives in `Personal` (public) | Lives in the private repo (`LightAISolutions/TourGuide`, owner-created) | Lives in the owner's Google account |
|---|---|---|
| Helper framework: generic Apps Script core, Telegram client, queue, Drive-mailbox bridge, envelope and bundle tools, test harness, deploy workflow, build agents and prompts | Routine-mode `CLAUDE.md` (persona + safety rules), skills, travel profile, per-trip memory, place notes, quarantine, daily log, `SESSION-CONTEXT.md` for build sessions | Drive `TourGuide/`: state Sheet, mailbox, research dossiers, finished brochures (HTML + PDF) |
| Shared kits: Maps client with budget guard, research contract, brochure design system and renderer, preference-reader pattern | `vendor/helpers/` — a pinned copy of `Personal/helpers/` so routines run the tools without loading this repo (§4.3) | Script Properties of the `tourguide-core` Apps Script project: bot token, admin secret, routine fire tokens, optional Maps and Claude API keys |
| Tour Guide generic code: schemas, visit-time estimator, planner and solver, brochure templates, the Apps Script feature pack, fixture trips with invented data | Routine prompt texts the owner pastes into the claude.ai routine editor | Claude HQ environment: Maps key as an **API credential** (§7); GitHub Actions secrets on this repo for clasp deploys (secrets are never readable from the public repo) |

Two consequences: the brochure *template* is public but a filled brochure never touches this repo or GitHub Pages; and this plan names no trip, place, person or account. The CI boundary check fails any push that adds files under personal-data paths (`profile*`, `people/`, `projects/`, `trips/`, `log/`, `quarantine/`) or matches secret and PII patterns (tokens, keys, e-mail addresses, phone numbers), with a planted-fake test proving it works.

### 4.3 How routines get the tools without loading this repo's `CLAUDE.md`

This repo's development `CLAUDE.md` (session-start checklist, bookends, pre-commit rules) would be harmful inside a routine. Two measures, both cheap:

1. **Routines attach only the private repo.** `helpers-dist.yml` publishes `helpers/` as a `helpers-dist` branch of this repo (public, so no credentials needed), and the private repo vendors it at `vendor/helpers/` with `git subtree` pinned to a commit. A `/update-helpers` step in each Phase 4+ session (and later a skill) bumps the pin with a reviewable diff. Phase 1 measures the alternative, a shallow clone of `helpers-dist` at run start, and picks one; the default is the subtree because it works offline, is deterministic and shows up in `git diff`.
2. **Routine-mode guard in this repo's `CLAUDE.md`** (Phase 1, three lines at the very top): if the session was started by a routine, ignore the rest of the file and follow the attached helper repo's `CLAUDE.md`. Defense in depth for the case where a routine attaches both repos anyway (fact 11 is partly an inference).

## 5. How each requirement is met

**5.1 Preferences — the interview first, connectors second.** The profile is built mainly from an **extensive interview in Telegram** (`/interview`, offered at `/start` while the profile is empty; decision 14): 25–40 questions in sections — pace and rhythm; food (cuisines, dietary needs, spice, street food versus sit-down, meal budget); activities; **heat, cold, humidity, rain and altitude tolerance**; mobility; crowds and timing; budget band; lodging style; companions; must-avoid; planning style and free time; languages; past favourite trips as free text — answered with buttons for closed questions and free text for open ones, resumable over days with a progress line, every question skippable, repeatable per section later. Closed answers are confirmed preferences and go straight into the profile through the prefs kit's decisions path (the only input that changes the profile); free-text answers become candidates the owner confirms with ✅ ✏️ ❌ like any other evidence. Skill `prefs-build` reads only the connectors the owner enabled for that routine as a **secondary** source — Gmail (hotel, flight, restaurant, ticket and tour confirmations), Calendar (past trips, events), Drive (trip documents) — plus the optional Google Takeout export of Maps saved lists and reviews dropped into Drive and, with the owner's OK, the travel-relevant lines of Assistant Brain's profile as a one-time seed; those propose candidates, never decide. Output: `profile/travel-profile.md` over the extended travel vocabulary (pace, interests, activities, food, dietary, spice, meal style, budget band, mobility, climate, crowds, day rhythm, lodging, companions, planning style, free time, transport, languages, must-avoid) and a short `profile_summary` the bot shows on `/profile`. Untrusted-content rules apply to every source; the interview answers are the owner's own words. Over time the profile also learns from what the owner does (§5.10): every shortlist tap, post-trip rating and calibration tap becomes evidence through the same kit.

**5.2 Autonomous deep web research.** Routines run without permission prompts, so research needs no approvals once the routine exists. Skill `trip-research` follows the research kit's contract: per-run budgets (searches, fetches, wall time), a source ledger (URL, date, what it supported), two independent sources for any fact the plan depends on, confidence labels, and injection handling (page text is data). It scores candidate places against the travel profile and writes a dossier to Drive plus `trips/<slug>.md`. Research is the middle of the `/plan` journey (§5.9): it starts from what the connectors already know about the trip (an **intake** scan for dates, lodging, flights and bookings that the owner confirms) and ends in a **shortlist** — activities and food, each with a one-line "why you" from the profile, an estimated visit time, the area, a Maps link and a confidence label — that the owner chooses from with buttons (decision 15) before anything is planned. Shortlist lines are the skill's own wording; page text never reaches the chat.

**5.3 Average visit duration.** No API provides it (fact 1), so the estimator triangulates: Google's "people typically spend" line when it appears in a search result snippet, the attraction's own guidance ("allow two hours"), tour and review sites' suggested durations, and travel guides → a min/max range, a chosen value adjusted by pace and interest, and the sources. After each trip a one-tap "longer / shorter / about right" per stop calibrates future estimates for that category.

**5.4 Route optimization with Google Maps.** The planner (node, tested on fixtures) (a) drops stops closed on the date or outside their hours, (b) clusters the trip's places into days by geography, lodging and constraints, (c) orders each day with a time-window-aware solver over a Route Matrix in the day's mode, including transit (fact 6: 100 elements per transit matrix, so clusters are capped at 10 stops or split), (d) fetches the real legs pair by pair with the planned departure time (fact 5), (e) inserts meals and free-time blocks by pace, and (f) emits a Google Maps directions link per leg and one per day (Maps URLs need no key). Driving and walking days also ask `optimizeWaypointOrder` (fact 4) and the plan explains any disagreement with the solver.

**5.5 Saved-for-later lists.** Every researched place keeps a status. Anything researched but not scheduled lands in a named Later list with the reason ("closed that day", "too far from day 2", "rainy-day backup", "the owner chose later"). `/later` lists, moves and promotes places back into a trip; promotions trigger a re-plan of the affected day only. Later lists are per trip; the place itself lives on in the places repository (§5.10), so a later trip to the same destination starts from it.

**5.6 Personalized notes per location.** Skill `place-notes` writes `places/<slug>.md` from the profile plus research: why it is on the list, what to do, see or eat, what to skip, best time of day, tickets and reservations, accessibility, nearby pairings. Notes are embedded in the brochure and shown by `/place`.

**5.7 Daily action plans and the brochure.** `plan-days` assembles each day: address, hours, closed days, Google rating and review count, website, activity and time budget, transit mode and minutes with the Maps link, free time, warnings, and a "verified on" date. `brochure-build` renders it with the brochure kit into one self-contained HTML document (inlined CSS and images, so it can also be a private Artifact, fact 9) and a print PDF: cover, trip at a glance, day spreads with a timeline rail and route sketch, place cards, "saved for later" appendix, practical info, attribution. Design quality gets its own work package with screenshot review (Phase 2c) and a second pass after the pilot (Phase 8). In the `/plan` journey one `plan` request carries the owner's choices and asks for all three deliverables, so `plan-days` chains `place-notes` and `brochure-build` in the same routine run (decision 16) and the bot receives the plan digest and the brochure together; the **PDF is sent into the Telegram chat as a document**, with the Drive link, as soon as it exists (decision 17).

**5.8 A chatbot like the Chief of Staff — three lanes.**
- **Lane A, instant (Apps Script, free):** structured asks are answered from the Sheet in under a second: `/trip`, `/today`, `/day 3`, `/later`, `/place <name>`, `/profile`, `/route A → B` (built-in Maps service, fact 8), "save this place", "move X to tomorrow" (a ✅ proposal when it changes a plan). Lane A also runs the **flows** — multi-step conversations the core drives per chat with buttons and free-text capture, their state kept in a Sheet tab so they survive executions and days: `/interview` is one flow, and `/plan <destination>` is a flow that orchestrates three Lane C requests and pauses between them (§5.9). The pack's envelope types (`shortlist`, `trip_facts`, `plan_digest`, `profile_summary`, `prefs_review`) arrive from the brain and are rendered as messages with buttons; the brochure PDF is sent as a Telegram document.
- **Lane B, fast free-text (optional, Claude API from Apps Script):** open questions that only need the current trip state ("what's near stop 3 with vegetarian food?", "how much free time on Thursday?") are answered by Sonnet 5.5 (Haiku 4.5 for trivial lookups) with the trip's plan JSON and notes as context, no tools, no web, inside the UrlFetch window (fact 8 inference). Key in Script Properties, off by default behind `CHAT_API_ENABLED` (decision 6). Paid per token outside the subscription (§8).
- **Lane C, deep (routine):** research, re-planning and anything needing the web or connectors ("find a quieter lunch near stop 3", "rework day 2 for rain") is written as a `req_<id>.json` envelope to `to-brain/`, then core fires the `chat` routine with only the request id as `text` (fact 9: fire text is untrusted, the envelope is the owner's words) and replies "working on it, ~N minutes" (a `/plan` costs three fires — intake, research, plan with notes and brochure — and each "more options" round one more). The routine answers with an envelope in `from-brain/` and then calls `WEBAPP_URL?route=wake`, an unauthenticated, idempotent, rate-limited route that only sweeps the mailbox and delivers replies (nothing a stranger could misuse). Fallback if the wake never arrives: one-off `after()` triggers at +3 and +10 minutes created at fire time, plus an hourly sweep while any request is open. **No permanent tick**, so the Tour Guide's share of the 90 trigger-minutes per day stays near zero (fact 8); Phase 5 measures it.

Why not route every message through a routine (the draft's implicit default): a routine run is a full session, takes minutes and draws on subscription usage, so it would make the bot feel broken for simple asks and burn usage on lookups. Lanes A and B give the Chief-of-Staff feel; Lane C gives the depth.

**5.9 The owner's journey — the product as the owner described it.** The bot is used in two moves: once, an interview that teaches it the owner's likes and dislikes; then, per trip, one command that does the research, asks for choices and delivers the brochure.

| Command | Lane | What happens |
|---|---|---|
| `/start` | A | Pairing (core). While the profile is empty, one line offers the interview with a button |
| `/interview [section]` | A → C | 25–40 questions, one per message, buttons or free text, progress line, skip, resumable; at the end one `prefs` request carries the answers; the brain applies the closed answers to the profile, sends the free-text candidates for ✅ ✏️ ❌ review (`prefs_review`) and a `profile_summary` the bot caches |
| `/profile` | A | The cached profile summary and buttons to redo a section |
| `/plan <destination>` | A orchestrates C | The journey below: three routine fires, the owner's choices in between, the brochure PDF in the chat at the end |
| `/trip` · `/today` · `/day N` · `/later` · `/place <name>` | A | Answered from the plan digest the core keeps in its Sheet; `/later` promotes with buttons → a `replan` of the affected days |
| `/places [query]` | A (🔁 → C) | Searches the places repository the core keeps in its `Places` tab — by name, tag or area — and shows each hit with its status, the trip it came from, the note line and a Maps link; buttons: 📝 full note (a `notes` request), ➕ add to the current trip (a Later entry with the owner's reason, then an offer to re-plan), 🔁 fresh check (a `places` request; §5.10) |
| `/review [trip]` | A → C | Offered once, the day after a trip ends: for each visited stop 👍 worth it · 👎 not · ⏭ skipped, then longer · shorter · about right; one `prefs` request at the end carries the taps (§5.3, §5.10) |
| `/replan <date> <why>` · `/notes` · `/brochure` | C | One request each; the reply (and a fresh digest or brochure) comes back through the mailbox and the wake route |
| `/route A → B` | A | Built-in Maps service, with a Maps link |
| free text | B or C | Lane B when enabled (decision 6), otherwise the `chat` routine |
| `/cancel` · `/help` · `/status` · `/pending` | A | Core: end the active flow; the built-ins |

The `/plan <destination>` journey (decisions 15–17):
1. **Intake.** The core creates the trip (a slug from the destination), opens a `research` request with scope `intake` and says it is looking at what it already knows. `trip-research` scans the enabled connectors — Calendar events, Gmail confirmations and Drive documents that name the destination in a plausible window — and answers with `trip_facts`: dates, lodging, flights, bookings, companions, each one line, plus what is missing. Found facts are untrusted content and wait in quarantine until the owner confirms them.
2. **Confirm.** The bot shows each fact with ✅ ✏️ ❌, asks by text for anything missing (dates first, lodging optional), then opens the real `research` request with the confirmed values.
3. **Research and shortlist.** `trip-research` first re-checks every place the repository already holds for that destination (§5.10), then runs the research kit's contract (budgets, source ledger, two-source rule, labels, injection handling), scores candidates against the profile, fetches Place Details through the Maps kit, writes the dossier and `trips/<slug>.md`, and answers with a `shortlist`: 8 activities and 6 food options per round, each with a why-you line, estimated minutes, area, Maps link and confidence label; places from an earlier trip come first, marked "seen before" with what changed. The bot shows them with ✅ want · 🔖 later · ❌ skip buttons, a *More options* button (one more fire per round, three rounds at most) and *Done choosing*.
4. **Plan, notes, brochure.** On *Done* the core opens one `plan` request with the picks, the later and skipped places and `deliverables: plan, notes, brochure`. `plan-days` plans only the chosen places (the rest stay candidates), runs `place-notes` for them and `brochure-build` in the same run, records every choice in the places' history and as preference evidence (§5.10), writes everything to Drive and answers with a `plan_digest`, a `places_digest` and a reply.
5. **Deliver.** The core stores the digest in its `Trips` / `DayPlans` / `Later` tabs, posts the day list and the Later reasons, sends the brochure **PDF into the chat** with the Drive link, and offers *replan a day* and *later list* buttons. From here `/today`, `/day N` and `/later` answer instantly, and `/replan` and Later-list promotions re-plan only the affected days.

What this costs: three routine fires per `/plan` (plus one per extra shortlist round), the same Maps volume as before (§8) and no permanent trigger. What it needs that the original plan lacked: the core **flows** primitive and `tgSendDocument` (Phase 4b, WP-1b), the interview question bank and the extended vocabulary in the prefs kit (WP-2f), choice handling and the five payload schemas in the engine (WP-3d), the matching skill deltas in the private repo (WP-4d), and Phase 5 built around this table. The v01.16r amendment adds the repository fields and a sixth envelope type to WP-3d and WP-4d, `/places` and `/review` to Phase 5, and the app as Phase 9 (§5.10–§5.11).

**5.10 The places repository and the learning loop — research is never wasted.** Every place the Tour Guide researches stays in `places/<slug>.md` in the private repo: one note per place, keyed by its Place id, shared by every trip (Phase 4 laid the memory out this way). The v01.16r amendment turns that file set into a **repository** with three additions:

- **History per trip.** Each place carries `history[]` — shortlisted · chosen · later · skipped · scheduled · visited · rated 👍/👎 · checked — with the trip and the date, plus `last_researched` and `last_verified`, and the destination it belongs to. The core mirrors the repository into a `Places` tab from `places_digest` envelopes (own data only), so `/places <query>` answers in a second when a plan goes wrong on the road: status, the trip it came from, the note line and a Maps link, with buttons to fetch the full note, add the place to the current trip (a Later entry with the owner's reason, then an offer to re-plan) or ask for a fresh check.
- **Re-check before re-research.** When `/plan` runs for a destination the repository already knows, `trip-research` begins with those places: a fresh Place Details snapshot (business status and hours — build-scoped, as always) and, when our claims are older than the re-check window (default 90 days), a fresh look at the official site. The result is a `PlaceCheck`: the brain's conclusion (open · temporarily closed · permanently closed · moved · unknown) with its sources, and `changes[]` in the brain's own words against the place's earlier research claims. Known places come first in the shortlist, marked "seen before — chosen last time" or "seen before — skipped last time" with the changes line; a place found closed goes to the trip's Later list with the reason instead of the shortlist. The weekly `trip-check` runs the same check on the scheduled places of an upcoming trip, and `/places` 🔁 runs it on demand (a `places` request answered by `trip-check`).
- **What may be stored.** The repository keeps place ids, our own research claims with their sources and dates, our notes, the owner's history and the dates we looked — never Google's hours, ratings, review counts, addresses, websites or business status (WP-2a: no caching permission beyond ids and 30-day coordinates). A re-check therefore compares against **our** earlier claims, and a `changes` line is the brain's sentence, not a stored Google value. Whether the place **name** — stored since Phase 3 — must come from the research run's own web sources rather than from a Places response is an open point for Phase 6's terms review (§9).

**The learning loop** is what makes the next plan more enjoyable than the last. Three kinds of taps become preference evidence through the prefs kit, each with `source_ref` `choice:<trip>:<slug>`: the shortlist's ✅ 🔖 ❌ (every shortlist item carries the dimensions it maps to, so a ✅ on a night market is weak evidence for *markets* and *street food*), the post-trip `/review` 👍 👎 per visited stop, and the calibration taps of §5.3. Positives are applied as confirmed — the owner's own tap is the confirmation; negatives are **held** until the same dimension is skipped or thumbed down twice (`--min-support 2`) and then reviewed with ✅ ✏️ ❌ like any other candidate: one skipped museum is a mood, two are a preference. The profile stays the only input to planning and the interview stays its primary source; the loop fine-tunes it. `plan-days` writes the choice evidence in the same run that plans the trip; `/review` sends one `prefs` request at its end.

**5.11 Beyond the chat — the options considered, and the Tour Guide app.** The owner asked whether a web app would gather trip information better and display the brochures. Seven ways to interact were compared against the four jobs chat does badly: a long form (the interview, intake confirmation), choosing from a shortlist with photos and a map, reading the brochure on screen (Telegram shows the PDF but not the responsive HTML), and browsing the repository with search, filters and a map.

| Option | Verdict |
|---|---|
| **A. Telegram bot only** (the plan as amended in v01.15r) | Stays the **front door**: every ask, approval, notification and on-trip change happens where the owner already is. Weak at the four jobs above |
| **B. Telegram Mini App — recommended** | A web page Telegram opens inside the chat from the bot's menu button or an inline button. It receives signed launch data (`initData`, HMAC-SHA256 keyed by the bot token), so the core can verify it is the owner **without any sign-in**; same phone, one tap, native look through Telegram's theme. Hosted as a **generic static shell** on this repo's GitHub Pages (no data in the page) that talks to the core's new `?route=app`. Costs one core registry (`registerRoute`), one verification helper and one pack file |
| C. Standalone web app on GitHub Pages behind this repo's Google sign-in wall (the `testauthhtml1` pattern, MasterACL) | Heavy for one user: Google sign-in on a phone, a GAS iframe, the ACL machinery the plan does not reuse (§2); a second front door with its own notifications; the plan had already ruled out a Tour Guide web page |
| D. Apps Script HtmlService web app ("only myself") | Google sign-in in a webview, Google's "created by another user" banner, a sandboxed frame; whether Telegram's launch data survives that frame is unverified. Rejected |
| E. Claude Artifact per trip (decision 5) | Read-only and already optional; cannot take choices or search the repository. Stays as is |
| F. Google Sheets / Drive as the UI | A free zero-build browser: the state Sheet's `Places` and `Trips` tabs are the owner's own data and can be opened any time. Kept, not the primary surface |
| G. Telegram inline mode (`@bot <query>` in any chat) | Pleasant for sending a place card to a travel companion; optional, after Phase 9 |

**The Tour Guide app (Phase 9, decisions 18–19).** Screens, in the order the pilot is expected to want them: the **shortlist** as cards (photo, the why-you line, minutes, area, a map around the day's lodging; ✅ 🔖 ❌ per card — the same callbacks the chat sends); the **brochure** on screen (the HTML from Drive rendered in a sandboxed frame, days as tabs, Maps links); **places** (search, filters by status, trip and tag, a card per place with the note line, a Maps link and 📝 ➕ 🔁); the **interview** as one scrollable form over the same bank, sections and skips; **trip facts** confirmation as a form. Everything the app does is the request or callback the chat would send, so the chat keeps working with the app switched off, and the owner can mix the two mid-journey. **Launch:** the bot's menu button (set once by a setup step) opens the app at its home; inline `web_app` buttons on shortlist, brochure and places messages open the right screen. **Hosting and trust:** the shell is one self-contained page under `live-site-pages/helper-app.html` (this repo's page conventions apply — version file, changelog, a standalone client-side page like `text-compare`), generic to the framework so a later helper reuses it; it carries no data, no key and no helper-specific text, and learns the core's URL only from the button that launched it (kept in Telegram's CloudStorage afterwards). Every request is a `text/plain` POST to `WEBAPP_URL?route=app` carrying the launch data; the core verifies the signature with `Utilities.computeHmacSha256Signature` (secret = HMAC-SHA256 keyed `"WebAppData"` over the bot token, data-check string of the sorted fields joined by newlines, constant-time compare), rejects an `auth_date` older than 24 hours and any user but the owner, rate-limits and audits, then dispatches by operation to the pack's handlers. Photos and live Google fields appear only when a card is opened — fetched at view time through the core's optional `MAPS_API_KEY`, shown with attribution, never stored — and Phase 9 verifies the photo SKU before switching photos on. **Inference (Phase 9 verifies before building):** an Apps Script "Anyone" deployment answers a simple cross-origin `text/plain` POST from the GitHub Pages origin with a readable JSON body — the pattern web sources describe for GitHub Pages → Apps Script; if it does not hold, the fallbacks are a GET-with-callback transport or the Artifact of decision 5. **When:** after the pilot (decision 19) — Phase 5's chat versions of every screen exist first, the pilot shows which screens matter, and Phase 8 finalizes the Phase 9 prompt from that evidence.

## 8. Costs and quotas

- **Google Maps Platform** (prices from fact 3): a trip with ~150 candidate places, ~40 scheduled stops and ~60 legs is about 150 Enterprise Place Details (+ ≤30 Atmosphere for notes), ~5 Text Searches, ~6 transit or driving matrices and ~60 Compute Routes calls → inside the monthly free caps (Enterprise 1,000, Pro 5,000, Essentials 10,000). Even at list price that volume is under $10. Guards, in layers: key restricted to Places + Routes; **per-API daily caps** in the Cloud console; a **budget alert** at a small amount; the kit's SKU counter refuses calls past a configured monthly ceiling. *Estimate, not a quote; Phase 8 reports real usage.*
- **Apps Script:** no permanent tick. Per deep request: the webhook execution, one `/fire` call, and at most two `after()` triggers of a few seconds each if the wake route fails, so the Tour Guide's trigger minutes stay near zero next to AB's 12–24 of 90 per day. Built-in Maps service: 1,000 direction queries per day is far above chat use.
- **Claude usage:** research, planning and brochure routines run per trip, not daily; a weekly `trip-check` is the only schedule. Each Lane C chat message is one routine run (subscription usage). Lane B, if enabled: ~200 questions a month at ~8k input / 1k output tokens on Sonnet 5.5 ≈ $5 per month at list price (fact 13); Haiku 4.5 halves it.
- **Per `/plan`:** three routine fires (intake, research, plan with notes and brochure) plus one per extra shortlist round — subscription usage, no API cost; the Maps volume is the trip estimate above; Telegram `sendDocument` is free (50 MB limit; a brochure PDF is typically a few MB, and the Drive link is the fallback). The interview is one fire at its end, not one per question.
- **GitHub Actions:** public repo minutes are free; the deploy job runs only when `helpers/` changes on `main`.
- **Places repository (v01.16r):** a re-check is one Place Details call per known place at the tier the shortlist needs anyway, plus a fetch of the official site when our claims are older than the re-check window — 40 known places are 40 Enterprise calls, inside the monthly free cap. The repository itself is markdown in the private repo and rows in the state Sheet: no storage cost.
- **The Tour Guide app (Phase 9):** the shell is a static page on this repo's GitHub Pages (free); each app call is one Apps Script execution like a webhook hit (no UrlFetch); photos and live Google fields are fetched at view time only, when the owner opens a card, and Phase 9 verifies their SKU before switching them on.
